# Exceptions

The exceptions defined by the message format library are unchecked and extend a single common base class,
`MessageException`. Catching them is never required, but the hierarchy is designed so that broad categories of errors
can be handled with a single catch clause or narrowed down to a specific exception type when precise control is needed.
Programming errors, such as an unknown message code or an invalid name, are reported with the standard Java
exceptions described under [Other Exceptions](#other-exceptions). Reading and writing pack files reports I/O problems
with the checked `IOException`.


## Exception Hierarchy

```text
RuntimeException
└── MessageException
    ├── MessageFormatException
    ├── MessageParserException
    ├── DuplicateMessageException
    ├── DuplicateTemplateException
    ├── MessageAdopterException
    └── FormatterServiceException
```


## MessageException

`MessageException` is the root of the hierarchy. It extends `RuntimeException` directly and does not add any behavior
beyond the standard constructors for a message string and an optional cause. Catching `MessageException` is a 
convenient way to handle every error that originates from the library in one place:

The examples on this page use the following message support.

```java title="Example setup"
import de.sayayi.lib.message.MessageFactory;
import de.sayayi.lib.message.MessageSupportFactory;
import de.sayayi.lib.message.exception.MessageException;
import de.sayayi.lib.message.exception.MessageFormatException;

import java.util.Locale;

var messageSupport = MessageSupportFactory.createDefault();
// all built-in formatters are available
```

```java
messageSupport.addMessage("order-summary",
    "Total: %{total,number:'#,##0.00'}");

try {
  messageSupport
      .code("order-summary")
      .with("total", 1234.5)
      .locale(Locale.US)
      .format();
  // "Total: 1,234.50"
} catch(MessageException ex) {
  System.Logger log = System.getLogger("messages");
  log.log(System.Logger.Level.ERROR, "Message formatting failed", ex);
}
```


## MessageFormatException

A `MessageFormatException` is thrown when something goes wrong while formatting a message or template at runtime.
Typical causes include a parameter formatter throwing an unexpected exception, an invalid configuration value such as
a malformed `DecimalFormat` pattern, and a post formatter name that has not been registered. The original exception
is available through `getCause()`. A template reference that cannot be resolved is not an error; it produces no text
(see [Templates](templates.md)).

While the exception propagates outward through the nested parts of a message, every level records where the failure
happened: the parameter, the template or the post formatter being formatted and, at the top, the message code and the
locale. Codes generated by the `MessageFactory` (`MSG[...]` and `TPL[...]`) are omitted, and the locale is only
recorded for localized messages.

The detail message returned by `getMessage()` is derived from the recorded context and names the parts that are
known. It is meant for logs and diagnostics. Its wording is not part of the API and may change in a later version.
For example, if the parameter `price` fails in a template that is
referenced from the mapped message of the parameter `onSale` in a message with the code `offer`, the detail message
currently reads:

```text
message 'offer' failed to format parameter 'price' in template 'price-tag' for mapped message of parameter 'onSale'
```

Code that catches the exception and rethrows it on a higher level can add context with `withCode`, `withTemplate`,
`withLocale`, `withParameter` and `withPostFormatter`. Each of these methods returns a new exception with the
additional context. The stack trace, the cause and the suppressed exceptions of the original exception are kept, so
the location of the failure is not lost:

```java
var message = MessageFactory.getSharedInstance()
    .parseMessage("%{price,number:'#0.0.0'}");

try {
  messageSupport.message(message).with("price", 9.5).format();
} catch(MessageFormatException ex) {
  // the detail message now includes the code 'order-summary'
  throw ex.withCode("order-summary");
}
```

The recorded context is available through `getCode()`, `getTemplate()`, `getLocale()`, `getParameter()` and
`getPostFormatter()`. Each of them returns `null` if the corresponding context has not been recorded. If several
parameters, templates or post formatters have been recorded, the innermost one is returned.

```java
messageSupport.addTemplate("price-tag", MessageFactory.getSharedInstance()
    .parseTemplate("%{price,number:'#0.0.0'}"));
messageSupport.addMessage("offer", "%{onSale,true:'%[price-tag]'}");

try {
  messageSupport
      .code("offer")
      .with("onSale", true)
      .with("price", 9.5)
      .format();
} catch(MessageFormatException ex) {
  ex.getCode();        // "offer"
  ex.getParameter();   // "price", the innermost parameter
  ex.getTemplate();    // "price-tag"
}
```

`getContextKey()` returns a key that identifies which kinds of context have been recorded. Its format is not specified
and may change, so it is only suitable for comparisons within the same library version.

The static factory method `MessageFormatException.of(Exception)` wraps any exception in a `MessageFormatException` if
it is not already one. If the argument is already a `MessageFormatException`, it is returned as-is.

/// note | Migration from 0.24
Up to version 0.24.0, the exception stored a single code, template, locale and parameter, and its detail message did
not describe nested parts correctly. The wording of the detail messages has changed. Code that parsed detail messages
must use the getters instead.

## MessageParserException

A `MessageParserException` is thrown when a message or template format string cannot be parsed. This happens at the
point where message format strings are converted into `Message` objects, either explicitly through the `MessageFactory` 
or implicitly when an adopter processes a message text.

In addition to the code, template and locale context fields (which work the same way as on `MessageFormatException`), 
the parser exception provides two properties that help pinpoint the error. The `getErrorMessage()` method returns a 
human-readable description of what went wrong, such as an unexpected token or a missing closing brace. The 
`getSyntaxError()` method returns a visual representation of the input showing exactly where the error occurred, 
similar to what a compiler would produce with a caret pointing at the problematic position.

Together, the `getMessage()` output combines all available context, the error description and the visual syntax error 
into a single string. For instance, attempting to parse the malformed format string `%{8}` as a message with code 
`MSG-003` and locale `zh-TW` produces:

```text
failed to parse message with code 'MSG-003' for locale Chinese (Taiwan): missing parameter name at '8'
  %{8}
    ^
```

A `MessageParserException` always indicates an invalid format string. The format string must be corrected, so the
exception is usually not caught at runtime. Messages declared through annotations or resource bundles report it while
they are adopted, which typically happens at application startup. The [Gradle plugin](../gradle-plugin/index.md)
reports it at build time.

The `withCode`, `withTemplate`, `withLocale` and `withType` methods allow the exception to be enriched as it
propagates. Like the methods of `MessageFormatException`, they return a new exception that keeps the stack trace and
the suppressed exceptions of the original one. The `withType` method accepts a `MessageParserException.Type` enum value
of either `MESSAGE` or `TEMPLATE`, which determines whether the diagnostic message reads "failed to parse message" or
"failed to parse template".


## DuplicateMessageException

A `DuplicateMessageException` is thrown when a message is added under a code that is already registered for a
different message. The `getCode()` method returns the duplicate code. The exact conditions, and how a filter replaces
them, are described under [Duplicate Handling](message-support.md#duplicate-handling).


## DuplicateTemplateException

`DuplicateTemplateException` is the counterpart of `DuplicateMessageException` for templates. It is thrown when a
template is added under a name that is already registered for a different template. The `getName()` method returns the
duplicate template name.


## MessageAdopterException

A `MessageAdopterException` signals that an error occurred while an adopter was reading messages or templates from an
external source. The annotation adopter throws it when scanning the class path fails, when a class path URL is invalid
or uses an unsupported protocol, when a class path archive is corrupt and when a class file cannot be found or read.
Other errors raised while the messages and templates of a class are adopted, such as a `DuplicateMessageException`, are
wrapped in a `MessageAdopterException` naming the class. The resource bundle adopter throws it when a resource bundle
for an explicitly requested locale does not exist. The underlying error is available through `getCause()`. A format
string that cannot be parsed is not wrapped. It propagates as a `MessageParserException`. Importing a pack file reports
errors as an `IOException`, not as a `MessageAdopterException`.

/// note | Migration from 0.24
Up to version 0.24.0, the annotation adopter wrapped every failure, including a `MessageParserException`, in a
`MessageAdopterException`. Code that handled invalid message syntax by catching `MessageAdopterException` must catch
`MessageParserException` as well.
///


## FormatterServiceException

A `FormatterServiceException` is thrown when registering a formatter violates a constraint enforced by the
`GenericFormatterService`. This includes situations such as registering a formatter for `Object.class` that does not 
implement the `DefaultFormatter` interface, registering a formatter whose name does not conform to kebab-case, 
providing an empty formatter name, registering a named formatter or a post formatter whose name has already been taken,
or registering a parameter configuration name that conflicts with an existing auto-apply formatter. A failed
registration leaves the formatter service unchanged.


## Other Exceptions

Besides its own exception types, the library uses the standard Java exceptions for programming errors. They indicate a
defect in the calling code and are best fixed rather than caught.

| Exception                       | Typical condition                                                                  |
|---------------------------------|------------------------------------------------------------------------------------|
| `IllegalArgumentException`      | `code(...)` is called with an unknown message code.                                |
| `IllegalArgumentException`      | A parameter, template, configuration or formatter name violates the naming rules. |
| `NullPointerException`          | A required argument, such as a message code or a parameter name, is `null`.        |
| `IllegalStateException`         | A `MessageBuilder` or a completed part builder is used again.                      |
| `IOException`                   | A pack file cannot be read or written, or exceeds a limit of the pack format.      |
| `UnsupportedOperationException` | `getMessageParts()` or `asFormatString(...)` is called on a localized message.     |

Whether a message code exists can be checked in advance with `MessageAccessor.hasMessageWithCode(String)`, which
avoids the `IllegalArgumentException` for codes that are only optionally defined.
