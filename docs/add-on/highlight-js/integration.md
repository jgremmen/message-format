# Integration

A highlight.js language is a function that highlight.js calls to obtain the language definition. It becomes usable
once it is registered with `hljs.registerLanguage(name, language)`. The three variants of the add-on contain the
same function and only differ in how a web page obtains it. This page shows the integration for each variant and
then covers the options, error handling, security, performance and common pitfalls.

The examples assume that highlight.js and the [files of the add-on](index.md#files) are served from the `/js` and
`/css` directories of the website. The messages in the
examples belong to a small online shop that greets its customers and reports the contents of their cart.


## Language Name and Aliases

The language should be registered under the name `message-format`. Its definition declares the aliases `msgfmt` and
`message-format`, so a code block can refer to it by either name. highlight.js finds the language of an element by
its class `language-message-format` or `language-msgfmt`.

```html title="Code blocks"
<pre><code class="language-message-format"
  >%{user,empty:'Guest'}</code></pre>
<pre><code class="language-msgfmt">%[item-count,n->cartSize]</code></pre>
<!-- both blocks are highlighted as message format strings -->
```

highlight.js adds the class `hljs` and the class of the registered language to every element it highlights. For a
block with the class `language-msgfmt`, the element also receives `language-message-format`. The stylesheets of the
add-on select elements by this class, as explained in [Styling](styling.md).

The language disables auto-detection. A code block without a language class is never highlighted as a message
format string, even if `hljs.highlightAll()` is used.


## Script Tag

The script variant `message-format.min.js` suits pages that load highlight.js with a plain `<script>` tag. When the
script runs, it looks for a global `hljs` object and registers the language as `message-format`. It must therefore be
loaded after highlight.js and before the page is highlighted.

```html title="Script tag"
<script src="/js/highlight.min.js"></script>
<script src="/js/message-format.min.js"></script>
<script>hljs.highlightAll();</script>
<!-- all message format code blocks are highlighted -->
```

The script also stores the language in the global variable `hljsMessageFormat`. A page that creates its own
highlight.js instance, or loads the script before highlight.js, registers the language from there.

```html title="Script tag with a separate instance"
<script src="/js/message-format.min.js"></script>
<script src="/js/highlight.min.js"></script>
<script>
  const highlighter = hljs.newInstance();

  highlighter.registerLanguage('message-format', hljsMessageFormat);
  highlighter.highlightAll();
  // the separate instance highlights the message blocks
</script>
```


## ES Module

The variant `message-format.mjs` is an ES module that includes the ANTLR runtime. Its default export is the
language, and the named export `createMessageFormat` creates a language with [options](#options). The module can be
imported directly in a `<script type="module">` or through a bundler.

```html title="Module script"
<script type="module">
  import hljs from '/js/es/core.min.js';
  import messageFormat from '/js/message-format.mjs';

  hljs.registerLanguage('message-format', messageFormat);
  hljs.highlightAll();
  // all message format code blocks are highlighted
</script>
```

In a project with an npm build, the module is imported by its [package name](index.md#files). The core of
highlight.js is sufficient, because the add-on does not depend on any other highlight.js language.

```js title="src/highlight.js"
import hljs from 'highlight.js/lib/core';
import messageFormat from 'highlightjs-message-format';

hljs.registerLanguage('message-format', messageFormat);

export default hljs;
// other modules import this instance with message format support
```


## ES Module with an External Runtime

The variant `message-format.lib.mjs` does not include the ANTLR runtime. It imports the runtime from the module
specifier `antlr4`, which the web project must resolve. This is useful when the project already uses ANTLR for other
purposes, because both can then share a single copy of the runtime.

The runtime must have exactly version 4.13.2. The lexer and parser in the add-on were generated by the ANTLR tool of
that version, and ANTLR only supports generated code together with the runtime of the same version.

A bundler such as Vite, webpack or Rollup resolves `antlr4` from the dependencies of the project. Without a bundler,
an import map tells the browser where to find the runtime. The `antlr4` npm package contains a browser build in
`dist/antlr4.web.mjs`.

```html title="Module script with an import map"
<script type="importmap">
  {
    "imports": {
      "antlr4":
        "https://cdn.jsdelivr.net/npm/antlr4@4.13.2/dist/antlr4.web.mjs"
    }
  }
</script>
<script type="module">
  import hljs from '/js/es/core.min.js';
  import messageFormat from '/js/message-format.lib.mjs';

  hljs.registerLanguage('message-format', messageFormat);
  hljs.highlightAll();
  // the runtime is loaded from the URL in the import map
</script>
```

Like the other variants, `message-format.lib.mjs` is minified and comes with a source map. Without the runtime, its
size is about 76 KB, or about 19 KB compressed with gzip.


## Highlighting Strings

`hljs.highlightAll()` and `hljs.highlightElement()` work on elements of the page. Some applications instead need the
highlighted HTML as a string, for example to build a table of messages or to render on a server. The function
`hljs.highlight()` returns an object whose `value` property contains the HTML.

The returned HTML only contains the `<span>` elements for the parts of the message. The class
`language-message-format` that the stylesheets of the add-on rely on is missing. The application must therefore wrap
the result in an element that carries both `hljs` and `language-message-format`.

```js title="Message table"
import hljs from 'highlight.js/lib/core';
import messageFormat from 'highlightjs-message-format';

hljs.registerLanguage('message-format', messageFormat);

const messages = {
  'cart.greeting': "Hello %{user,empty:'Guest'}!",
  'cart.count': '%{n,format:choice,0:\'no items\',:\'%{n} items\'}'
};

const rows = Object.entries(messages).map(([ key, message ]) => {
  const html = hljs.highlight(message,
      { language: 'message-format' }).value;

  return `<tr><td>${key}</td><td><code class="hljs ` +
      `language-message-format">${html}</code></td></tr>`;
});
// rows contains one table row per message, with highlighted code
```

highlight.js escapes the message text in the returned HTML, so a message containing `<` or `&` cannot inject markup.
The message key in the example is inserted without escaping, which is only acceptable because the keys are
constants of the application.


## Options

The default export is a language with default options. A language with other options is created with
`createMessageFormat(options)`. In the script variant, the same function is available as `hljsMessageFormat.create`.
The function takes an object with the following options and returns a new language.

| Option       | Type    | Default | Description                                                         |
|--------------|---------|---------|---------------------------------------------------------------------|
| `markErrors` | boolean | `false` | Wraps syntax errors in an additional scope `deletion`               |

Most themes color the scope `deletion` red or with a red background. Marking errors is useful for an editor preview
or for a page that checks messages, where invalid syntax should stand out.

=== "ES Module"

    ```js title="Marking syntax errors"
    import hljs from 'highlight.js/lib/core';
    import { createMessageFormat } from 'highlightjs-message-format';

    hljs.registerLanguage('message-format',
        createMessageFormat({ markErrors: true }));

    hljs.highlight('%{user,@}', { language: 'message-format' }).value;
    // the invalid character @ and the closing } are marked as errors
    ```

=== "Script Tag"

    ```html title="Marking syntax errors"
    <script src="/js/highlight.min.js"></script>
    <script src="/js/message-format.min.js"></script>
    <script>
      hljs.registerLanguage('message-format',
          hljsMessageFormat.create({ markErrors: true }));
      hljs.highlightAll();
      // syntax errors in all message blocks are marked
    </script>
    ```

Registering a language under a name that is already registered replaces the previous definition. The script variant
registers the language with default options when it is loaded, and the second call in the example replaces it.


## Error Handling

The language never throws an exception and never loses text. Every character of the input appears in the output in
its original order, whether the message is valid or not. This matters for editors, where a message is highlighted
while it is still being typed and is incomplete most of the time.

For an invalid message, the parser recovers from the error and continues. The parts it can still recognize are
highlighted by their meaning in the syntax. Tokens outside of a recognized part are highlighted by their kind alone.
A name becomes a variable, a number a number, a delimiter a delimiter, and so on. Characters that the lexer rejects
are emitted without any scope. Syntax errors are not reported on the browser console.

With `markErrors` enabled, the scope `deletion` marks the token at which the parser detected the error, as well as
characters rejected by the lexer. The token at which the error is detected is not always the one that is wrong. In
`%{user,format:}`, the formatter name is missing, but the error is detected at the closing `}`, so the `}` is marked.
An error at the end of the input is not marked, because there is no token left to mark. The incomplete message
`Hello %{user` is therefore highlighted without any error marker.

```js title="Error markers"
import hljs from 'highlight.js/lib/core';
import { createMessageFormat } from 'highlightjs-message-format';

hljs.registerLanguage('message-format',
    createMessageFormat({ markErrors: true }));

const check = message =>
  hljs.highlight(message, { language: 'message-format' })
      .value.includes('hljs-deletion');

check("Hello %{user,empty:'Guest'}!");  // false, the message is valid
check('%{user,format:}');               // true, the } is marked
check('Hello %{user');                  // false, the error is at the end
```

Messages with extremely deep nesting, in the order of several hundred nested parts, exceed the stack depth of the
parser. The language then highlights all tokens by their kind alone, without the nested `subst` and `string` scopes.
Real messages are far below this limit.

An error marker means that the add-on's parser rejects the message. Since the add-on is generated from the grammar of
the Java library, a message that the Java parser accepts is also accepted here, provided that the add-on and the
library have the same version. The highlighting does not check anything beyond the syntax. An unknown formatter
name or a configuration key that no formatter supports is highlighted like any other name.


## Security

highlight.js escapes all text that the language passes to it. Highlighting an untrusted message with
`hljs.highlight()` therefore produces safe HTML, as shown in [Highlighting Strings](#highlighting-strings).

The risk lies in how the message gets into the page before highlighting. `hljs.highlightElement()` reads the text
content of an element. If the application builds that element by inserting the untrusted message as HTML, the
browser interprets the markup before highlight.js sees it.

/// danger | Unsafe Insertion of Untrusted Messages
The following example inserts a message from an untrusted source with `innerHTML`. A message such as
`<img src=x onerror=alert(1)>` runs script code in the page, regardless of the highlighting.

```js title="Unsafe"
const block = document.querySelector('#preview');

block.innerHTML = untrustedMessage;
hljs.highlightElement(block);
// UNSAFE: markup in the message is interpreted by the browser
```
///

The safe way is to set the text with `textContent`, which never interprets markup.

```js title="Safe"
const block = document.querySelector('#preview');

block.textContent = untrustedMessage;
hljs.highlightElement(block);
// the message is shown as text and highlighted
```


## Concurrency

JavaScript code in a page runs on a single thread, so the question of thread safety from the Java side does not arise
in the same form. The language keeps no state between two highlighting calls. Each call creates its own lexer and
parser. The same language function can therefore be registered with several highlight.js instances, and highlighting
in one instance does not affect another.


## Performance

Every highlighting call lexes and parses the complete message. Nothing is cached between calls, so highlighting the
same message twice costs the same as highlighting it once. For typical messages of a few hundred characters, the
work is small compared to rendering the page.

The larger cost is loading the add-on. The variants that include the ANTLR runtime add about 190 KB to the page, or
about 50 KB with gzip compression.

/// tip | Load the Add-On Only When Needed
On a site where only some pages show messages, the ES module variant can be loaded on demand with a dynamic
`import()`. Pages without message blocks then do not load the add-on at all.

```js title="Loading on demand"
import hljs from '/js/es/core.min.js';

const blocks = document.querySelectorAll(
    'code.language-message-format, code.language-msgfmt');

if (blocks.length > 0) {
  const { default: messageFormat } =
      await import('/js/message-format.mjs');

  hljs.registerLanguage('message-format', messageFormat);
  blocks.forEach(block => hljs.highlightElement(block));
}
// the add-on is only loaded when the page contains message blocks
```
///

When the web project already contains the ANTLR runtime, the variant `message-format.lib.mjs` avoids loading it a
second time, as described in [ES Module with an External Runtime](#es-module-with-an-external-runtime).


## Common Pitfalls

If message blocks are shown without any highlighting, the language was most likely not registered when the page was
highlighted. The script variant only registers itself when highlight.js was loaded before it. A call to
`hljs.highlightAll()` that runs before the language is registered leaves the message blocks unchanged. highlight.js
reports such blocks on the browser console with a message that the language could not be found.

If the code block has no class at all, highlight.js tries to detect the language automatically. Because the language
disables auto-detection, the block is highlighted as some other language or not at all. Every message block needs the
class `language-message-format` or `language-msgfmt`.

If escape sequences or delimiters look exactly like the surrounding text, the stylesheets of the add-on are missing,
or the highlighted HTML is not inside an element with the class `language-message-format`. This often happens with
HTML from `hljs.highlight()`, which has to be wrapped as shown in [Highlighting Strings](#highlighting-strings).

If the variant `message-format.lib.mjs` is used, the version of the `antlr4` runtime is not checked at any point.
Neither the add-on nor the generated parser compares it with the version the parser was generated with. A project
that resolves `antlr4` to a version other than 4.13.2 uses an unsupported combination without any warning. Pinning
the exact version in the dependencies of the project avoids this.

If highlighting has no effect at all, the highlight.js version may be too old. The hook that the language relies on
does not exist in highlight.js versions before 11.8, so the language cannot work with them. The add-on declares 11.9
as its minimum version.
